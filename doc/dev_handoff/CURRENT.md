## 2. 已完成的阶段性小闭环

最近几轮后端实施，已围绕 `backend/app/api/oracle_adg.py` 完成以下阶段性收口：

### 2.1 主库关键字段与检查口径已做过修正
- 主库 Oracle 版本已从旧口径向 `v$version` 解析方向收口
- 主库 SERVICE_NAME 已按 `select name from v$active_services;` 获取，并改为包含关系校验
- 主库监听已切到 `lsnrctl status` / 端口占用检查口径
- 主库监听预检查已拆成：
  - 监听状态
  - 监听端口校验
- 主库 ORACLE_BASE 已按“用户输入优先，否则环境变量 / profile 探测”方向处理

### 2.2 备库边界已做过关键收口
- `standby_oracle_base` 已按安装环境探测方向处理
- `standby_service_name` 已按“无输入默认等于 standby_db_unique_name”方向处理
- 备库版本已按安装环境优先：
  - `sqlplus -v`
  - `cd $ORACLE_HOME/OPatch && ./opatch lsinventory | grep -i "Oracle Database"`
  - 失败再 fallback 主库版本
- 第 2 步中 standby 不再被硬要求 SQL 可连，已去掉“必须 standby SQL 可连”这一前置边界假设

### 2.3 版本兼容性与目录类检查已做过一轮收口
- 主备版本兼容性已不再是“字符串不等即 fail”
- 已进入“三段式”方向：
  - 完全一致：pass
  - 差异较小：warn
  - 差异过大：fail
- 目录类检查当前行为已按最新需求方向处理：
  - 不存在：fail
  - 有文件 / 使用率高（85%以上） / 无权限：warn
  - 其余：pass

## 3. 必须明确：当前还不能宣称“第 2 步整体完成”

### 3.1 还没有证据证明“所有字段都已逐项对齐”
`step2_latest_requirements_and_design.md` 的目标不是只修少数字段，而是要求把第 2 步整体稳定收口为三层合一页面：

1. 字段最终展示值
2. 字段来源标签
3. 结构化预检查结论

当前最多只能确认：若干关键字段与后端边界已分轮修正。
**还不能直接等价为：所有主库字段、所有备库字段、所有环境摘要字段、所有预检查项都已逐项对齐。**

### 3.2 预检查提示模块的最终目标仍未完成
最新真源明确要求：
- 预检查提示模块不能继续停留在“标题 + 简单列表”的旧展示结构
- 后端返回必须足够支撑前端组装：
  - 标题
  - 说明
  - 原因
  - 等级
  - 是否阻断
  - 分组
  - 关联字段

当前这一块仍未完成最终收口，必须单独作为后续阶段处理。

### 3.3 前端统一展示层联动还未确认完成
最新真源明确要求：
- 每个字段在前端都必须同时具备：
  - 最终展示值
  - 来源标签
  - 对应的预检查结果入口

当前还不能确认前端已经全面按这一规则收口。
因此，当前不能把后端阶段性修正误写成“前后端整体完成”。

### 3.4 环境摘要 / 配置摘要 / 预检查提示三块仍需严格区分
最新真源要求三块不能混用：
- 搭建方式信息：配置摘要
- 搭建环境信息：环境摘要
- 预检查提示模块：校验结论

这一整体结构化收口仍属于后续工作，不应在当前阶段被默认视为已完成。
